P.A.R.A. × Domain-Driven Design

From Domains to Areas

Mapping Tiago Forte's P.A.R.A. onto Eric Evans' Domain-Driven Design for a multi-agent AGI framework.

P.A.R.A. is a personal knowledge-management method: it sorts everything into Projects, Areas, Resources, and Archive. That taxonomy is excellent at telling us what kind of thing an item is, but it says nothing about ownership, invariants, or lifecycle. When autonomous agents act on those items, the missing structure becomes dangerous: a permanent responsibility gets mistaken for a disposable task, and an agent happily "completes" a duty that never had an end date.

Domain-Driven Design supplies exactly the missing vocabulary. By mapping each PARA category onto a DDD pattern, we give every bucket an explicit bounded context, a clear owner, and rules about what may change and when.

Projects — transient → Application Services / Sagas Short-lived, orchestrated, compensatable workflows.
Areas — perpetual → Core Bounded Contexts / Aggregate Roots Long-lived, invariant-protecting, own their language.
Resources — shared knowledge → Shared Kernel / Supporting Subdomain Deliberately shared model reused across contexts.
Archive — historical state → Event Store / cold storage Append-only history, replayable, low-cost.

Goal. Give autonomous agents explicit long-term bounded contexts instead of treating ongoing responsibilities as one-off tasks. An ongoing responsibility (an Area) must never be modeled as a disposable, completable task (a Project). DDD is what prevents that category error.

System flow: intent → agents → AOM → human vision

User intent is routed into both the project (transient) and area (perpetual) worlds, then fused by an Adaptive Object Modeling engine whose output is surfaced to human judgment.

The AOM connection: why the bottleneck moves

Once the model is runtime metadata, changing a domain stops being a code change. That removes coding as the constraint — and promotes human governance to the top of the queue.

Old paradigm

Coding is the bottleneck — engineers hand-write domain classes; every domain change requires code, review, and redeploy.

New paradigm

AI generates/alters AOM runtime metadata on the fly — new types, attributes and rules are metadata, so coding is no longer the bottleneck.

The bottleneck has shifted from coding to human governance.

The three human governance pillars

Adapt

Keeping AOM metadata and domain boundaries aligned as reality changes.

Train

Feedback loops, RLHF, and domain grounding to prevent hallucinated rules.

Secure

Guardrails, sandboxing, context isolation, and access control to stop autonomous agents from breaching invariants or escalating privilege.
